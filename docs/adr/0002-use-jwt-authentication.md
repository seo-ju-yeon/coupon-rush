# ADR-0002: JWT 기반 인증 및 인가 적용

## 상태

Accepted

## 결정일

2026-09-09

## 배경

초기 구현은 API 요청에서 사용자 ID를 직접 전달받았습니다. 이 방식은 요청자가 실제 사용자 본인인지 확인할 수 없고, 다른 사용자의 ID로 쿠폰을 발급하거나 주문을 생성할 수 있다는 문제가 있습니다.

회원가입, 로그인, 사용자 식별과 역할 기반 접근 제어를 일관된 방식으로 처리할 인증 체계가 필요했습니다.

## 검토한 선택지

- 서버 세션 기반 인증
- 직접 작성한 JWT 필터와 인증 처리
- Spring Security OAuth2 Resource Server의 JWT 지원

## 결정

- Spring Security OAuth2 Resource Server로 Bearer JWT를 검증함
- 로그인 성공 시 HS256으로 서명한 Access Token을 발급함
- JWT의 `subject`에는 사용자 ID를, `role`에는 사용자 역할을 저장함
- 비밀번호는 BCrypt로 해시한 값만 PostgreSQL에 저장함
- 인증 및 권한 오류는 공통 JSON 응답으로 반환함

## 결정 이유

- Spring Security가 서명, 만료시간과 발급자를 표준 방식으로 검증함
- 서버에 로그인 세션을 저장하지 않는 Stateless API를 구성할 수 있음
- JWT의 사용자 ID로 쿠폰 발급자와 주문 사용자를 식별할 수 있음
- 역할 클레임을 `ROLE_USER`, `ROLE_ADMIN` 권한으로 변환해 API 접근을 제한할 수 있음

## 영향

### 장점

- 클라이언트가 전달한 사용자 ID를 신뢰하지 않고 검증된 토큰에서 사용자를 식별함
- 인증 로직을 각 Controller에 반복하지 않고 Spring Security에서 처리함
- 서버가 여러 대로 늘어나도 로그인 세션 저장소를 공유할 필요가 없음

### 단점

- HS256 비밀 키가 유출되면 공격자가 유효한 토큰을 만들 수 있으므로 환경 변수로 안전하게 관리해야 함
- 발급된 Access Token은 만료 전까지 즉시 취소하기 어려움
- 현재는 Refresh Token과 로그아웃에 따른 토큰 폐기 정책을 제공하지 않음

## 후속 규칙

- JWT 비밀 키를 소스 코드와 Git에 저장하지 않음
- 운영 환경에서는 충분히 긴 무작위 비밀 키를 사용함
- 사용자 식별이 필요한 API는 요청 본문의 사용자 ID가 아닌 JWT의 `subject`를 사용함
- 토큰 재발급과 강제 로그아웃이 필요해지면 Refresh Token 및 폐기 정책을 별도로 결정함
