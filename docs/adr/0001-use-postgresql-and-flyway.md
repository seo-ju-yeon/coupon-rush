# ADR-0001: PostgreSQL과 Flyway 사용

## 상태

Accepted

## 결정일

2026-09-09

## 배경

Coupon Rush는 사용자, 쿠폰, 발급 내역과 주문 사이의 관계를 저장해야 합니다. 쿠폰 발급에서는 중복 발급과 초과 발급을 막기 위해 유일 제약조건, 외래 키, 체크 제약조건과 트랜잭션이 필요합니다.

애플리케이션이 성장하면서 스키마 변경 이력을 코드와 함께 관리하고, 개발 및 테스트 환경에서 같은 순서로 적용할 방법도 필요했습니다.

## 검토한 선택지

### 데이터베이스

- PostgreSQL
- MariaDB
- 테스트 및 개발 환경에서만 사용하는 인메모리 데이터베이스

### 스키마 관리

- Hibernate의 `ddl-auto`로 스키마 생성
- SQL 파일을 수동으로 실행
- Flyway 마이그레이션

## 결정

- 운영 데이터베이스와 테스트 데이터베이스로 PostgreSQL을 사용함
- 모든 스키마 변경을 `src/main/resources/db/migration`의 Flyway SQL로 관리함
- Hibernate는 `spring.jpa.hibernate.ddl-auto=validate`로 설정함
- 통합 테스트에서는 Testcontainers로 실제 PostgreSQL을 실행함

## 결정 이유

- 외래 키, 유일 제약조건과 체크 제약조건으로 데이터 정합성을 DB에서도 보호할 수 있음
- 동시성 테스트를 실제 운영 DB와 동일한 SQL 및 락 동작으로 검증할 수 있음
- Flyway가 스키마 변경 순서와 적용 이력을 `flyway_schema_history`에 기록함
- 애플리케이션이 스키마를 임의로 변경하지 않고 엔티티와 스키마의 불일치를 시작 시점에 발견할 수 있음

## 영향

### 장점

- 개발, 테스트와 배포 환경에서 같은 마이그레이션을 적용할 수 있음
- 스키마 변경 내용을 Git 이력으로 검토할 수 있음
- H2와 PostgreSQL 사이의 문법 및 락 동작 차이로 인한 테스트 오류를 줄일 수 있음

### 단점

- 기존에 적용된 Flyway 파일은 내용을 수정하지 않고 새 버전 파일로 변경해야 함
- 통합 테스트를 실행하려면 Docker가 필요하며 단위 테스트보다 실행 시간이 길어짐
- 로컬 실행 전에 PostgreSQL 컨테이너를 준비해야 함

## 후속 규칙

- 적용이 끝난 마이그레이션은 수정하지 않음
- 스키마 변경은 `V4__...sql`처럼 새로운 버전 파일로 추가함
- JPA 엔티티를 변경할 때 대응하는 마이그레이션과 통합 테스트를 함께 작성함
